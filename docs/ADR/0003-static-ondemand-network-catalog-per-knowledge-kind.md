# One static OnDemand network catalog per knowledge kind

Context: the `publishing_to_network` stage POSTs a Beckn `catalog/publish` envelope to the external Discovery Service after DEV ingest, but the payload was a hardcoded `"catalogs": []` stub — and the spec declares `message.catalogs` as `minItems: 1`, so every publish the pipeline had made was invalid. Nothing was noticed because the client only called `raise_for_status()` and never read the per-catalog verdict in `message.results[].status`, which the spec is explicit about ("a 200 does **not** mean every catalog was accepted"). What a seeker actually needs from this provider is to know it *can* answer agricultural questions from an ingested corpus; the corpus itself lives in Qdrant and is served through the AI layer, not through the network envelope. The `network-specs` schema pack (`schema-packs-v0.1`) offers exactly one field for that distinction: `informationMode`, `OnDemand` or `Direct`.

Decision:
- Announce **knowledge kinds, not documents**. One catalog per `documents.document_kind`, holding exactly one resource, identical no matter how many documents of that kind have been ingested: `oan.knowledgeprovider.advisory` and `oan.knowledgeprovider.schemes`. Every document of a kind re-publishes the same envelope.
- `informationMode: OnDemand` on both resources. That is what makes the static shape correct rather than a shortcut: OnDemand means "invoke me for the specifics", and the schema *forbids* the fields that would carry specifics (`issuedAt`, `recommendations`, `rationale`, `source`, `supportingResourceIds`, `validity` on an advisory; `content`, `provenance`, `knowledgeType`, `lifecycleStatus`, `version`, `supersedes` on a knowledge resource). A per-document catalog would have to be `Direct` and ship recommendations we do not have in that form.
- Resource ids (`oan.knowledgeprovider.advisory.resource`, `...schemes.resource`) are **permanent**. `publishDirectives.updateMode` is sent explicitly as `MERGE`, which upserts resources by id; a renamed id therefore strands the old resource on the network instead of replacing it, and the `FULL` alternative deletes anything a payload omits — too sharp a default to leave implicit.
- Schemes are typed `openagrinet:KnowledgeResource` with `subjectCategories: ["Scheme"]`, not `openagrinet:KnowledgeAdvisory`. There is no `KnowledgeScheme` schema in the pack; `Scheme` exists only as a `subjectCategories` enum value on `AgricultureResource`. This costs one extra required field (`supportedKnowledgeTypes`) and means the two kinds do not share a resource-attributes template.
- Any other `document_kind` — the `'document'` default, `'video'`, or an operator-entered custom slug — publishes **nothing**: no HTTP call, and a `network_publish_skipped` artifact so the stage still completes. `document_kind` is a free-form slug (`DOCUMENT_KIND_RE`), so an unmapped kind is the normal case, not an error.
- `topics`, `subjectCategories` and `languages` are module constants in `pipeline/network_catalog.py`, not environment variables. v2 replaces them with per-document values derived by an AI agent, so configuring them now would mean documenting variables we intend to withdraw.

Alternatives considered:
- **One catalog entry per document, with `informationMode: Direct`.** Rejected: `Direct` requires `issuedAt`, `recommendations` and `source` per resource, and an ingested PDF does not decompose into structured recommendations without the AI layer that v2 introduces. It would also grow the catalog without bound and make every re-ingest a network write.
- **Reuse `KnowledgeAdvisory` for schemes with `subjectCategories: ["Scheme"]`.** Rejected: one schema and one code path, but a scheme catalogue is reference material, so it would be matched by advisory-intent discovery queries and missed by reference-intent ones — a wrong answer in both directions to save a few lines.
- **Track published catalog ids and publish each one only once.** Rejected: it buys fewer network calls at the cost of persistent state, a "force republish" escape hatch, and staleness whenever the constants above change. `MERGE` on a stable resource id already makes repeat publishes idempotent, and re-sending means a transient failure self-heals on the next document.
- **Announce the full `subjectCategories` enum on the advisory resource** (`Crop`, `Livestock`, `Weather`, `Market`, `Practice`) rather than `["Crop"]`. Rejected for now, knowingly: it fits OnDemand semantics better, but it over-claims against today's corpus. The mismatch is real — a livestock advisory is currently announced as `Crop` — and is the first thing v2's per-document derivation fixes.
